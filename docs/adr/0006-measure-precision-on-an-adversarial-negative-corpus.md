# 6. Measure precision on an adversarial negative corpus, not just recall

- Status: accepted
- Date: 2026-08-30

## Context

The project generates its own evaluation corpus: `datagen.py` writes a small
repository with defects planted at known `file:line` positions, and `evaluate()`
scores the run against that manifest.

The first version reported recall only - how many planted defects were found.

## Problem

Recall alone is trivially gameable and, worse, it is gameable *by accident*. A
rule loosened until it fires on anything vaguely shaped like the defect scores
100% recall, and the corpus cannot tell the difference. For a linter that is the
failure mode that actually matters: developers disable tools that cry wolf, and
they disable them permanently.

Counting false positives needs somewhere they can be counted. A finding on a file
with planted defects might be a real defect the manifest simply does not list, so
it cannot be scored as wrong.

## Options considered

1. **Recall only.** The status quo. Rejected above.
2. **Count every finding not in the manifest as a false positive.** Rejected: the
   planted files contain incidental defects, and punishing the analyzer for
   finding real problems teaches the wrong thing.
3. **Run against a large real repository and hand-label the findings.** The most
   honest signal available, and not reproducible: it needs a checkout the
   repository cannot ship and a labelling pass nobody can re-run in CI.
4. **Write a second set of files that are deliberately clean, and count any
   finding on those as a false positive.**

## Decision

Option 4. `negatives.py` writes 14 files that contain no defects, and precision is
counted on those files only. They are written to be adversarial rather than easy
- each one is the shape that *resembles* a defect:

- `API_KEY_HEADER = "X-Api-Key"` - a name that matches the secret detector's
  name pattern, holding a header name;
- `hashlib.md5(blob, usedforsecurity=False)` - the caller stating in the API's
  own vocabulary that the hash is not a security control;
- `range(len(xs) - 1)` used for pairwise iteration, where the off-by-one is
  correct;
- `ast.literal_eval` next to the rule that fires on `eval`;
- functions sitting exactly on the complexity and parameter ceilings.

`codesentry eval` reports per-rule true positives, false positives, false
negatives, precision, recall and F1, and a test fails if any rule in the table
has no planted defect.

## Reasoning

A rule is only measurable if something can prove it wrong. Pairing each rule with
the look-alike it must stay quiet on turns "the rule fires" into a two-sided
question, and it makes the corpus a regression suite: tightening a heuristic
later cannot silently trade precision away.

Requiring a negative for every new rule (CONTRIBUTING.md, and the pull request
template) is what keeps that property as the rule table grows.

## Trade-offs

- Precision is measured on 14 small synthetic files. That is not a prediction
  about anyone's real codebase, and the README says so in the same section as
  the number.
- Writing a good negative is harder than writing the rule. It is the part of a
  rule contribution most likely to stall.
- The corpus is generated by the same repository it evaluates, so a
  misunderstanding shared between the rule and the corpus is invisible to both.
  Only outside reports fix that, which is why the false-positive issue template
  asks for the source file directly.

## Consequences

- `codesentry eval` is a CI step, so a regression in either direction fails the
  build rather than being noticed later.
- The measured numbers in the README are quoted with the command that produced
  them and the size of the corpus in the same breath, because a bare "100%
  precision" would be a claim the evidence does not support.
